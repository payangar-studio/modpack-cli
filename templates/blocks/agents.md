## Modpack socle

This repository is a Minecraft modpack managed with `modpack-cli` (`modpack`). The repository is the source of the pack; the Modrinth instance on this machine is fed from it, one way only, and the published packs are built from it.

### What is where

- `mods.lock.toml`: the manifest, the one list of the pack's mods (key, path, hashes, side, platform ids). Generated by the CLI.
- `mods/`: the jars, ignored by git. `modpack install` downloads the missing ones, and removes those it downloaded that the manifest no longer lists (recorded in `.modpack/local/`, ignored by git).
- `mods-local/`: the jars no platform serves (an abandoned mod, a development build, a file from its author), tracked by git. A jar dropped there becomes a `local` entry of the manifest; it is published only once approved with `modpack approve <key>`.
- `config/`: the base configuration, shared by every variant.
- `variants.toml`: the variants (the default one is the full pack; every other variant removes or adds mods by key) and the conditions each variant must meet. Its syntax and every condition with its options: [`variants.toml` reference](https://github.com/payangar-studio/modpack-cli/blob/main/docs/variants.md).
- `overrides/<variant>/config/`: configuration that applies to one variant only, written over `config/`.
- `page/`: the project page, pushed to the platforms.
- `audit/last.toml`: the last audit report, written by the `modpack-audit` skill.
- `.modpack/`, `.claude/skills/modpack-*/`, `.github/workflows/modpack-*.yml` and this block: the socle. `.modpack/README.md` says who owns what.

### Use the CLI, not your hands

| To | Run |
|---|---|
| Prepare a fresh clone on this machine: git hooks, jars, Modrinth instance, default variant | `modpack setup [--no-launch]` |
| Bring the socle of this repository to the CLI's version | `modpack update` |
| See the state of the instance: loaded variant, drift, unknown jars, stale manifest | `modpack status --json` |
| Add a mod from Modrinth, CurseForge or a local jar, to every variant or to the variants named (`--variant` repeats; `--variant default` alone: the default variant only) | `modpack add <mod> [--version <v>] [--variant <variant>]... [--with-deps]` |
| Remove a mod from the repository and from every variant (deleting its jar does not) | `modpack remove <key>` |
| Update the manifest after adding or changing a jar in `mods/` or `mods-local/` (a missing jar keeps its entry) | `modpack manifest` |
| Approve a local mod for publication, once its jar is reviewed (a changed jar loses its approval) | `modpack approve <key>` |
| Replace a local mod by its published version, under the same key | `modpack add <slug>` |
| Download the missing jars | `modpack install` |
| List the variants, load one into the instance | `modpack variant list`, `modpack variant load <variant>` |
| Check the conditions of the variants | `modpack test [variant] --json` |
| Build the packs | `modpack pack [variant] --json` |
| Push `page/` to the platforms that have an API (never in CI) | `modpack page push [--platform <platform>]` |
| See which platform secrets are set, without their values | `modpack auth --status` |
| Create a new pack repository, elsewhere | `modpack init [dir]` |

Every command runs without a terminal: a missing value is an error that names the argument to pass. Never pass `--force` without the user's go: it overwrites what they changed.

### Never

- Edit `mods.lock.toml` by hand: change `mods/` through `modpack add`, `modpack remove` or `modpack manifest`.
- Run `modpack approve` without the user's go: approving a local mod is their review of the jar.
- Change anything in `.modpack/` or in the socle's skills and workflows: `modpack update` rewrites them.
- Write into the instance to change the pack: change the repository, then load the variant.
- Print, ask for or store a secret. The platform keys go through `modpack auth`, in the user's own terminal, or through the environment.

### Logs and crash reports

`modpack status --json` gives the instance's directory in `instance.path`. Its game logs are in `logs/` (`latest.log`, and `debug.log` on NeoForge) and its crash reports in `crash-reports/`. Read them there; never change files of the instance by hand.

### Skills of the socle

- `modpack-return`: bring what changed in the instance back into the repository (mods tried from the app, configuration changed in game).
- `modpack-audit`: audit what changed since the last audit (new mods, known conflicts, sources, platforms, orphan configuration).
- `modpack-source`: read the source code of a mod, on the version the pack runs.
- `modpack-curseforge-page`: create or update the CurseForge project page from `page/`.
